- **换声 CPU 与 DML 对比**（同片段、同 key）：单次推理 DML 34–44 秒、CPU 29–40 秒（CPU 的 F0 2.6–8.4 秒、合成 24 秒），同进程连续 3 次 CPU 全部成功。两者输出有可测的系统性差异——模式内频谱余弦相似度 DML 0.988、CPU 0.990，跨模式 4 组均为 0.912–0.913。A/B 样音在 `data/song/auditions/换声模式对比-篇章24s-核显DML(现行).mp3` 与 `…-CPU.mp3`（data/ 不入库），需操作者试听裁定。

**任务 2 设计选项**：
- **R 常驻工作进程**（任务书原设想）：服务启动即加载，之后每首省下换声启动约 20 秒与分离启动约 8 秒。代价——常驻约 1GB 工作集与 4.3GB 提交内存（无人点歌时也占）；同进程反复推理在 DML 下触发设备移除，必须切到 CPU（输出随之改变，见上）；需另做崩溃重启、取消 = 杀进程重建、空闲回收与两路并发；仅「重启后的第一首」比下一项多受益。
- **P 每任务流水预热（建议采用）**：任务一开始就并行拉起换声进程，完成导入与模型加载后等待指令；分离与音高分析完成后下发路径与 key，推理一次后进程退出。稳态每首同样省约 20 秒；进程只活一个任务，无常驻内存；保持「每进程一次推理」的隔离与取消语义，现行已验收的 DML 换声输出不变。代价——一个带行协议的工作脚本与 `pipeline.ts` 的并行编排；等待中的工作进程占约 0.9GB 工作集（并发上限 2）。
- **W 系统缓存预热**：服务启动后（唱歌开启且工具链齐全时）后台跑一次只导入不推理的进程，把磁盘读取与杀软首次扫描挪到启动期。零常驻内存，只对重启后的第一首生效，可与 P 叠加。
- 可叠加的提速项（均改变已验收行为，需操作者决定并复听）：换声切 CPU（稳定性；约 −5 秒）；音高分析换 yin（约 −16 秒）；分离 `shifts=0`（约 −5 秒）。P 加后两项估计把热态单首从约 137 秒降到 100 秒左右。

**任务 3 结论**：原样迁移到 torch-directml 不可行。实测把 htdemucs 放到 DirectML 设备上前向，DirectML 以致命错误 `Invalid or unsupported data type ComplexFloat` 中止进程，没有可捕获的 Python 异常。原因是混合模型的 STFT / iSTFT、`cac` 模式下时间分支前段的复数卷积、维纳滤波都使用复数张量，而 torch-directml（RVC runtime 自带的 0.2.5，亦为最新稳定版）不支持复数。可行路径要把整条前向改写成实数运算并在 CPU 与核显之间搬运，属于对第三方模型的深度改造；且本机核显 DML 在重负载下已有设备移除的前科，直播时核显还要同时承担显示与直播姬。环境上 Demucs 环境是 torch 2.14.1（无 DirectML），迁移需降级到 2.4.1 并另建环境。**建议不做**；分离步的提速转向上面的 CPU 参数与估计器替换。回退方案（若将来另做）：保留现 whaletalk-song 环境不动，GPU 路径作为独立可选环境并自动回退到 CPU 环境。
