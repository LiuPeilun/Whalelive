# 代码审查与修复协作

审核方负责代码审查与复审，Zcode 负责代码修复和修复记录，用户手动发起每轮工作。

## 目录约定

按月份创建 `YYYY-MM` 目录，每轮审核使用 Asia/Shanghai 时间命名文件，时间戳格式为 `YYYY-MM-DD_HHMMSS`。

```text
docs/reviews/
├─ README.md
├─ LATEST.md
└─ YYYY-MM/
   ├─ YYYY-MM-DD_HHMMSS-review.md    审核方生成的本轮结论
   └─ YYYY-MM-DD_HHMMSS-fixes.md     Zcode 修复后生成的简短记录
```

`*-review.md` 保存审查基准、范围、问题编号、代码位置、复现依据和验证限制。报告完成时标记 `document_status: complete`，审核方检查报告后更新 [LATEST.md](LATEST.md) 指向该报告。

`*-fixes.md` 由 Zcode 在同一月份目录创建，与对应审核报告使用相同时间戳，逐项记录修复情况与证据。修复记录可以随本轮进度补充，审查报告作为历史记录保留。

复审在对应月份目录创建新的时间戳报告，并在新报告中引用上一轮报告及其修复记录。

## 怎样读取最新审核

1. 读取固定入口 [LATEST.md](LATEST.md)，打开其中链接的审核报告。
2. 确认报告文档状态为 `complete`，根据入口给出的同时间戳文件位置记录修复。
3. 阅读该报告中的审查基准和未关闭问题，再处理对应修复。
4. 复审沿用原问题编号，继承仍待处理的项目，新问题分配新编号。

入口缺失或链接失效时，在月份目录内按 `*-review.md` 文件名中的审核时间排序，选择文档状态为 `complete` 的最新报告，并修正入口。

审核方在新报告完成后更新入口。Zcode 将处理结果写入对应的修复记录，报告中的审查基准用于确定修复范围。

## 修复分支与提交

`main` 用于集成经过复审与相关验证的版本。每个独立修复批次从目标 `main` 基线创建 `fix/<阶段>-review-<日期>` 分支，例如 `fix/p0-review-20261114`。

同一批问题在合并前的补充修复与多轮复审沿用该修复分支。提交按问题或紧密相关的改动分组，便于审查与回退。新的独立修复批次使用新的分支。

修复分支可以推送到远端用于备份与协作，复审结论和相关检查结果共同确定合并时机。合并后，后续批次从更新后的 `main` 开始。

审核报告记录实际审查分支、基准提交和目标提交。修复记录包含修复分支、起点提交与完成提交，尚未提交的工作同时列出文件和差异范围。复审后新增的代码改动进入下一次核查，报告中的目标提交用于定位已覆盖的代码版本。

## 固定流程

1. 用户发起代码 review，审核方读取实际代码与差异，创建本轮 `YYYY-MM-DD_HHMMSS-review.md`。
2. 用户让 Zcode 读取最新审核，Zcode 核对审查基准，在本批修复分支逐项核查并按当前架构修复。
3. Zcode 在同一月份目录生成同时间戳的 `YYYY-MM-DD_HHMMSS-fixes.md`，说明改动和验证结果。
4. 用户发起复审，审核方直接核对代码差异、回归用例与实际行为。
5. 审核方创建新时间戳报告，记录已验证修复、仍存在、待验证及新增问题，完成后更新 `LATEST.md`。
6. 本批问题完成复审和相关验证后，将修复分支合并到 `main`，记录最终集成版本。

每个问题的修复记录作为复审索引，关闭状态由审核方依据实际代码和验证证据确定。

## Zcode 修复记录

保持简短，每个问题占一行或一个小节。建议包含以下内容。

- 对应的 `*-review.md` 和审查基准提交。
- 修复分支名称、分支起点提交和当前目标提交。
- 修复后的提交号。尚未提交时记录当前 HEAD、未提交文件和差异范围。
- 问题编号、处理状态、修改文件与修复方式。
- 实际执行的测试命令及通过或失败结果。
- 浏览器、OBS 的实测范围，以及待验证内容。
- 对审查结论有异议时提供代码依据或复现结果。

参考结构如下。

```markdown
# 本轮修复记录

对应审核为同一月份目录中的 <同时间戳>-review.md。
修复分支为 <branch>。
修复基准提交为 <commit>。
修复后提交为 <commit>，或说明未提交差异。

| 问题编号 | 处理状态 | 修改位置与方式 | 验证结果 |
| --- | --- | --- | --- |
| WT-P0-001 | 已修复待复审 | 文件与简短说明 | 命令与结果 |

## 实测与待测

填写浏览器、OBS 的实际测试范围和待验证项目。
```

## 审核记录的验证范围

报告分别记录静态检查、自动测试、内存复现、浏览器实测与 OBS 实测。缺少环境或证据的项目保留为待验证。

复审时核对修复提交与当前工作区。若代码在审查期间变化，在报告中记录实际覆盖的版本与差异范围。
