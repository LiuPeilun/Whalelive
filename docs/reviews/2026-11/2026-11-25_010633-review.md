# P3 点歌与唱歌管线首轮审查

暂不通过。新增 2 项 P1、6 项 P2、1 项 P3。审查覆盖 `be6e929` 到 `535b317` 的一个提交，入场工作区干净。WT-P2-017 仍开放，本轮隔离实例加载旧版辽宁小北配置后仍继承 `+20Hz`。WT-P2-011～016 保持关闭。[上轮审核](2026-11-24_220419-review.md)

## WT-P3-001 · P1 · 控制台无法保存任何设置

设置面板重建 `PUT /api/settings` 请求体时漏传 `singing`，服务端现已要求该字段。用隔离 Fastify 实例读取设置，构造与面板相同形状的提交，收到 `400 VALIDATION_FAILED`，错误为 `singing: 必须是对象`，设置版本未递增。补上原 `singing` 后，同一实例可正常保存。该回归影响音色、礼物规则和队列等现有设置。复验通过面板修改一个旧字段，确认保存、刷新后回读，以及原有 `singing` 值保留。[面板组装](../../../src/web/control/features/settings-panel.ts#L226) · [服务端校验](../../../src/server/modules/settings/schema.ts#L144)

## WT-P3-002 · P1 · 后台任务并发无上限，部分任务无法紧急取消

每个缓存未命中的不同歌名都会立即启动管线。`prune()` 按记录数量删除最早条目，活跃任务也会被删；`cancelAll()` 只能找到仍在映射里的任务。使用真实唱歌模块和可控管线替身挂起 42 个不同请求，42 个管线全部启动。第一个任务从映射消失，紧急停止只中止其余 41 个。随后兑现第一个任务，仍写入成片并调用入队回调。直播中多名观众点不同歌时，会同时争用 CPU、内存和磁盘，并可能在停止后产生旧表演。[清理策略](../../../src/server/modules/singing/index.ts#L87) · [直接启动](../../../src/server/modules/singing/index.ts#L189) · [取消范围](../../../src/server/modules/singing/index.ts#L204)

另在最后的 MP3 编码阶段按停。编码函数没有超时或 `AbortSignal`，编码替身在停止后仍完成并留下临时 MP3，成片回调被拦截。四步管线的中止也先发起 `taskkill` 再立即结算，工作目录清理与子进程退出可能重叠。复验应覆盖有界等待与运行队列、所有在途任务可追踪、最后编码也可取消，以及确认退出后清理，随后恢复可接新歌。[编码调用与返回](../../../src/server/modules/singing/index.ts#L126) · [子进程停止](../../../src/server/modules/singing/pipeline.ts#L72) · [MP3 编码](../../../src/server/modules/singing/pipeline.ts#L205)

## WT-P3-003 · P2 · 成片挤满队列后，弹幕和大航海无法入队

成片优先级为 35，现有腾位条件只允许聊天或优先级至多 30 的条目作为候选，高档答谢的补救路径只找小额礼物。隔离实例设置容量为 5，在暂停时通过成片回调填满五条，再经实际 HTTP mock 入口提交普通弹幕和大航海，两条都返回 `queue-full`。复验应覆盖满队列的正常直播优先级，保证歌曲能为高优先级互动腾位，并记录实际淘汰结果。[成片优先级](../../../src/server/modules/interaction/index.ts#L432) · [当前腾位](../../../src/server/modules/interaction/queue.ts#L65) · [高档答谢补救](../../../src/server/modules/interaction/index.ts#L716)

## WT-P3-004 · P2 · 指定歌手仍可能选中同名错版或无关视频

`rank()` 只看关键词的第一段，`MV`、`官方`等加分还能压过不含歌名的惩罚。用实际 Python 排序函数回放候选，输入 `篇章 乙歌手 MV`，两个同名官方 MV 同分，结果选中了排第一的甲歌手。另一组中，无关标题 `其他歌 官方MV` 排在有精确歌名和歌手的 `篇章 乙歌手` 前。排序之后直接选首条并缓存成片。复验应包含同名不同歌手、无关高分项、搜索为空和无可靠匹配，确认选中版本对应用户查询。[打分规则](../../../scripts/song/steps/fetch.py#L40) · [直接选首条](../../../scripts/song/steps/fetch.py#L72)

## WT-P3-005 · P2 · 成片缓存忽略渲染配置，且歌曲写入无容量约束

缓存只用规范化歌名作为键。用同一标题预置成片，之后改切片起点、时长和目标音高，再点歌仍命中原文件。若调整音高或修正模型、择源，已有成片仍照常复用。歌曲通过 `cache.store()` 直接写入，现有音频缓存仅在 TTS `AudioCache.put()` 时触发淘汰。隔离数据目录写入 201 个新的歌曲样本后，共留有 202 个歌曲文件。复验应覆盖同配置复用、变更影响成片的配置后重新生成、歌曲连续写入的明确上限和待播文件的保留。[缓存键与写入](../../../src/server/modules/singing/cache.ts#L13) · [查找调用](../../../src/server/modules/singing/index.ts#L165) · [现有淘汰入口](../../../src/server/infrastructure/audio-cache.ts#L51)

## WT-P3-006 · P2 · 能保存的配置可让换声必然失败，或绕过已知输入上限

设置 API 接受 `keyMin=6.5`。输入中位恰为目标音高时，钳位结果为 `6.5`，Python `int('6.5')` 抛 `ValueError`。同时，`clipSeconds` 仍允许至 90 秒，四步管线会把整段送入转换。开发记录已注明该 RVC 包在 40 秒的换声输入上崩溃。复验应对齐配置与后端可处理范围，覆盖半音非整数、允许值边界，以及超出安全时长时的拒绝或实际分片。[设置范围](../../../src/server/modules/settings/schema.ts#L104) · [钳位](../../../src/server/modules/singing/keys.ts#L4) · [Python 转换入口](../../../scripts/song/steps/convert.py#L27) · [长输入记录](../../ROADMAP.md#L422)

## WT-P3-007 · P2 · 缓存点歌会先唱，事后才确认，接单结果也只反映确认语

在空闲且持音频租约的隔离实例，发送缓存命中点歌后，实际 WebSocket 派发顺序是 `35`（歌曲）再 `40`（确认语）。原因是命中时 `requestSong()` 同步回调并触发播放，确认项此时还未入队。同一接线也在创建任务后才试入确认队列，队列满时 HTTP 可以返回 `accepted:false`，实际后台处理已经启动。复验应让接单结果反映真实任务状态，并验证首次与缓存命中两种路径的确认、派发、拒收顺序。[确认顺序](../../../src/server/modules/interaction/index.ts#L414) · [成片回调与调度](../../../src/server/modules/interaction/index.ts#L432) · [命中同步通知](../../../src/server/modules/singing/index.ts#L180)

## WT-P3-008 · P3 · 日志和任务状态记录的 key 与实际换声参数不同

四步管线先从输入基频计算并传入 `convert.py`，返回时却优先采用输出基频。上层再用返回值算一次 key，任务状态、回调和日志记录的是第二次结果。用原有管线和确定性子进程回放，输入中位 205 Hz、输出中位 300 Hz，转换收到 `+7`，上层记录 `+1`。真实冒烟中成片日志也报 `key=1`，这个值不能作为实用移调量的验收证据。缓存命中时回调则固定报告 `0`。复验应分别记录输入基频、实际传入的 key 和输出基频，缓存复用沿用可信元数据或标记未知。[参数和返回值](../../../src/server/modules/singing/pipeline.ts#L179) · [上层重算](../../../src/server/modules/singing/index.ts#L119) · [缓存占位](../../../src/server/modules/singing/index.ts#L185)

## WT-P3-009 · P2 · Windows 子进程输出乱码会破坏中文数据路径

三个 Python 步骤会输出原样 Unicode JSON，Node 却固定按 UTF-8 解码每个输出块。真实冒烟的 `chosenTitle` 已乱码。用包内 Python 在同样的重定向管道中回放含 `C:/song/审查/clip.wav` 和 `篇章` 的 JSON，Python 报 stdout 编码为 `gbk`，Node 获得损坏的路径和标题。后续 Demucs 会拿到该损坏路径。以 Python UTF-8 模式回放，两字段无损。复验应固定子进程协议编码、使用跨数据块的解码方式，并用中文数据目录走一遍分离至媒体发布。[Node 解码](../../../src/server/modules/singing/pipeline.ts#L91) · [路径传给 Demucs](../../../src/server/modules/singing/pipeline.ts#L157) · [Python 输出](../../../scripts/song/steps/fetch.py#L94)
