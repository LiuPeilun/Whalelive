## WT-P3-002（P1）急停可能永久占住两份点歌配额

审查复现链的三个环节分别修复：

1. **已取消信号不再回退 spawn-per-job**（`pipeline.ts` runPipeline）：`await worker.whenReady` 之后先核对中止信号——已中止直接抛 `PipelineStepError('convert','aborted')`，不再进入回退分支（旧路径会在已取消信号下启动 convert.py 子进程）。
2. **`runStep` 已取消分支改为拒绝**：原实现在 signal 已中止时先 spawn 再走取消分支提前 `return`，未注册 `error`/`close` 监听，Promise 无终态。改为 spawn 之前检查，已中止立即 `reject('aborted')`，不启动子进程（该提前返回原本是不可达的防御代码，worker 回退路径使其可达）。
3. **中止的结算统一等子进程 close 确认**（`spawnConvertWorker`）：`onAbort` 只发起 taskkill，不再即时 `resolveReady(null)`/`failConvert('aborted')`——等待就绪时由 close 交付 `resolveReady(null)`，推理中由 close 交付拒绝（`tail='aborted'`）。推理超时同样只发起杀树、由 close 结算。上层 `execute` 的 catch 在子进程确认退出后才 `settleCancelled`（清理工作目录 + 释放配额），与既有 runStep/encodeMp3 的「kill 后等 close 再结算」契约对齐。

回归：`pipeline.test.ts` 新增两条真实 Windows 子进程替身用例——等待就绪期间中止（挂住的 worker 被杀、拒绝 `aborted`、不产生 convert.py 痕迹）；推理期间中止（指令送达替身后急停，close 确认后才拒绝）。`index.test.ts` 新增「急停任务结算后配额释放，可重新受理」——cancelAll → 管线拒绝 → 任务落 `failed('cancelled')` → 在途归零 → 新点歌立即受理。

## WT-P3-027（P2）就绪后提前退出跳过回退

- `ConvertWorkerHandle` 新增 `hasExited()`（`exitCode`/`signalCode` 判定）；runPipeline 派发条件改为 `device !== null && !worker.hasExited()`——按下发指令时的进程状态决定回退，就绪后提前退出的 worker 改走 spawn-per-job。推理已开始后的失败仍按现有路径直接失败（不二次回退）。
- 回归：`WORKER_MODE=ready-exit` 替身（打印 ready 后立即退出）→ 管线经回退成功，工作目录有 convert.py 痕迹、无 worker 指令痕迹。

## WT-P3-028（P2）服务关闭后启动预热仍继续运行

- `warmConvertRuntime` 返回 `WarmupHandle { stop(), done }`：`stop()` 经 AbortController 触发杀树；`done` = worker `whenClosed`（进程退出后 resolve）。就绪时不再主动杀进程——`endStdin` 已让脚本加载完 EOF 自退。
- `app.ts`：句柄存入 `singingWarmup`，`close()` 中 `stop()` 后 `Promise.race([done, 5 秒])` 等退出（有界，防 taskkill 异常阻塞关停）。
- 顺带收紧预热与首个任务的并发冲突（审查冒烟中观察到的 `UnicodeDecodeError` 回退）：预热进程以 `WHALETALK_CONVERT_DEVICE=cpu` 强制 CPU 加载（convert-worker.py 支持）——磁盘与杀软预热与推理设备无关，避免两个进程同时初始化 DirectML。
- 回归：`WORKER_MODE=hang` 的预热进程只能靠 `stop()` 终止，断言 `done` 在 5 秒内兑现；happy path 用例改为等待 `done` 并断言预热完成日志。
