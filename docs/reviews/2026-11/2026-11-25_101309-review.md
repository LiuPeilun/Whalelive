## WT-P3-006 · P1 · 配置迁移会取整所有合法的唱歌比例参数

旧版 40 秒值迁移为 24 秒，设置保存成功，这两项复验通过。但 `sanitizeSinging()` 共用的 `clamp()` 对每个数字调用 `Math.round()`，包括允许小数的切片起点、索引混合、清辅音保护和 RMS 混合。全新目录的版本默认值 `0.4 / 0.3 / 0.33 / 0.25`，实际生效全部为 `0`，切片从开头开始，索引混合归零。此回归覆盖全新安装与现有配置。[迁移实现](../../../src/server/modules/settings/index.ts#L78)

通过真实设置接口保存 `0.4 / 0.7 / 0.33 / 0.25`，`PUT` 返回 `200` 并原样响应，重新 `GET` 却读到 `0 / 1 / 0 / 0`。实际后台管线收到的是后者。旧配置的 `clipStartRatio: 0.75` 读取后变成 `0.9`。复验需区分取整字段与连续字段，保证新默认、合法小数的保存回读和传入管线的值一致，旧超长片段仍迁移到安全范围。[保存回读路径](../../../src/server/modules/settings/index.ts#L117) · [配置用于取歌](../../../src/server/modules/singing/pipeline.ts#L174)

## WT-P3-002 · P2 · 编码已等待退出，急停仍遗留临时 MP3

延迟退出的管线替身验证通过。两个任务在途时连按两次急停，两者退出前仍占用两份配额，不启动第三条管线。待旧任务退出后新任务可启动。真实 Windows FFmpeg 复验也确认，急停后任务先处于 `cancelling`，子进程 `close` 后才变为 `failed`，没有发布成片。上轮 P1 的过早释放问题已消除。[占用统计](../../../src/server/modules/singing/index.ts#L205) · [取消阶段](../../../src/server/modules/singing/index.ts#L273) · [等待进程退出](../../../src/server/modules/singing/pipeline.ts#L261)

同一真实编码复验中，退出后仍留下 262144 字节的临时 MP3。`encodeMp3()` 在 `close` 后拒绝 Promise，`execute()` 的 `catch` 调用 `settleCancelled(job, null)`，没有传入缓存目录中的临时文件路径。持有 `outMp3` 的中止分支仅在编码 Promise 成功兑现时可走。复验需覆盖编码已写部分数据后急停、超时和编码失败，等进程退出后实际检查临时音频及工作目录。[临时路径](../../../src/server/modules/singing/index.ts#L151) · [异常收尾](../../../src/server/modules/singing/index.ts#L173)

## WT-P3-004 · P2 · 长歌名的得分仍可抵消缺失的歌手

原用例 `篇章 乙歌手 MV` 只有甲歌手候选时已经拒绝。用实际 `fetch.py` 的 `main()` 替换搜索响应和下载函数，查询 `My Heart Will Go On 席琳迪翁 MV`，只提供 `My Heart Will Go On 甲歌手 MV`。五个歌名词和 `MV` 一共加 10.5 分，缺失指定歌手扣 5 分，总分 5.5 仍越过门槛，进入下载。复验需覆盖多词歌名搭配明确歌手，以及候选集中只有错版的场景。[打分](../../../scripts/song/steps/fetch.py#L45) · [进入下载前的判断](../../../scripts/song/steps/fetch.py#L86)

## WT-P3-005 · P2 · 新近写入豁免无法保住旧缓存点播

用生产默认的十分钟豁免重跑原用例。把超过十分钟的缓存成片通过实际点歌入口放入暂停队列，媒体 `HEAD=200`。再写入 30 个新曲缓存，原歌曲仍在队列中，媒体已返回 `404`。缓存命中不改变旧文件的写入时间，且缓存淘汰不读取播放引用。达到硬上限时，新文件同样会失去时间豁免。复验需同时覆盖旧缓存再点和高写入压力，直到播放终态、取消或丢弃为止，媒体在实际需要时都能读取。[歌曲淘汰](../../../src/server/modules/singing/cache.ts#L29) · [通用音频淘汰](../../../src/server/infrastructure/audio-cache.ts#L29)

## WT-P3-007 · P2 · 满载时缓存仍被拒，未接单仍被报告为成功

真实 HTTP 入口下挂起两条冷管线，再点一首已有成片和一首新歌。两者均返回 `accepted:true`，原确认语和补发的繁忙提示都进入队列，最终没有新歌曲入队，也没有新后台任务。代码仍在查缓存之前执行配额不足的提前返回，与修复记录所述顺序不符。繁忙分支返回的是补发提示能否入队，日志与请求状态仍不能一致表达实际未接单。复验应让满载时已有成片正常入队，未接的新歌只给真实繁忙提示并呈现对应接单结果，正常接单仍保持确认先于演唱。[配额检查与缓存顺序](../../../src/server/modules/singing/index.ts#L205) · [确认与更正提示](../../../src/server/modules/interaction/index.ts#L423)
