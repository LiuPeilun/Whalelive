## WT-P1-009 · 启动锁仍可被另一启动器删除

采纳复审建议改用**操作系统管理的互斥机制**,彻底放弃文件锁:

**启动锁 = 专用回环端口的监听 socket**(`scripts/lib/test-server.mjs`,`StartLock` 类,协调端口默认 32109,可用 `WHALETALK_STARTLOCK_PORT` 更换):

- 获取 = `net.createServer().listen(32109, '127.0.0.1')` —— **绑定是内核原子操作,谁绑上谁持有**;失败(EADDRINUSE)即他人持有,等待重试;
- 持有者崩溃 → 操作系统立即关闭并释放端口 → **无需任何文件回收逻辑**,复审的两个竞态(独占创建后写 nonce 前暂停被竞争方判空陈旧回收;第二次读取后删除前被换主后按旧结果删除)在「无删除操作」的设计下不存在;
- 释放 = `server.close()`;协调端口被无关程序占用时**明确失败**(报错含更换指引),不误伤;
- 端口锁内的 PID 登记文件沿用 wx 独占创建;读到**空 PID 文件**不再报「启动进行中」而是回收重占——空文件只可能是前一持有者写 PID 前崩溃的残留,启动锁内无并发,自愈安全。

**回归 harness 三场景(重写后 11/11)**:

1. **PID 写入失败**(EIO 注入,临时端口):启动报错 ✓ → 端口不再监听 ✓ → 登记释放 ✓ → 立即重试启动并可停止 ✓;
2. **无关程序占用协调端口**(替身监听 32109):启动 4s 超时明确失败 ✓ → **替身不受影响仍可响应** ✓;
3. **空端口并发两个启动器**:恰好一个存活 ✓ → 败者以「已有活跃测试服务」退出 1 ✓ → 胜者健康并可停止 ✓。
