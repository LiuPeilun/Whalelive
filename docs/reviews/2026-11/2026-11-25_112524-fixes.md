`cache.store()` 的 `writeFileSync`/`renameSync` 包 try/catch：失败时清理 `song-*.mp3.<pid>.tmp` 临时发布文件后原样抛出——上层 `execute` 既有失败路径负责任务终态，临时文件不再残留（审核用例：目标文件名被测试目录占据导致 `renameSync` 失败的场景）。

## WT-P3-007 · P2 · 预判/接口结果/任务终态不一致 —— 已修复（结构性重排）

- **可接性判定单一来源**：新增模块方法 `assess(title)`（返回 `{cached, reusable, acceptable}`）——`probe()` 与 `requestSong()` 共用同一判定，杜绝预判漂移。语义统一：cached=成片存在（零成本不受配额）；reusable=同标题在途可复用（不受配额，但 **cancelling 排除**——急停中的任务不会产出成片）；acceptable = enabled && (cached || reusable || 活跃<配额)，**cancelling 计入活跃占用**。
- **缓存命中分支接住回调结果**：`requestSong` 缓存命中改为先建 queued 任务 → `onSongReady` → 成功才 `touch(ready)`，队列满失败 → `fail(queue-full)` + 返回 `busy-limit`（冷歌路径同理：`onSongReady` 先于 ready touch）。审核场景（满载时点缓存歌谎报接单）不可复现——失败即如实标记与返回。
- **复审三个边界**：①同标题正常运行+满载 → probe 判 acceptable（reusable）→ 复用返回 ok，确认语"这就来" ✓；②两条 cancelling → probe 判 unacceptable → 确认语直接"排满了"，无"正在准备"矛盾序列 → requestSong busy-limit → 返回未受理 ✓；③满队 + 缓存命中 → 确认入队 → 成片回调 queue-full → job 标 failed → 返回未受理 ✓。
