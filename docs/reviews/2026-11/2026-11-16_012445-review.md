## WT-P0-007 · P2 · 续租被拒后取消了全部租约恢复入口

主要位置在 [lease-result 失败处理](D:/Project/dsh-workspace/WhaleTalk/src/web/overlay/main.ts:149)，相关位置为 [清空租约及两个计时器](D:/Project/dsh-workspace/WhaleTalk/src/web/overlay/main.ts:91)。

### 复现与实际结果

1. 使用合法配置 ttlMs=3000、renewIntervalMs=1000，正常登记并取得租约。
2. dance 播放时仅抑制 lease-renew 的发送，业务连接保持开启，并在失效前排入 wave。
3. 服务端回收旧租约，dance 立即以 LEASE_LOST 结算，wave 携带空租约派发。
4. wave 起播后恢复续租发送，页面向服务端提交旧租约续租，收到 LEASE_EXPIRED。
5. 观察到 wave 正常 ended，并回到 idle。这部分已修复。
6. 页面在收到拒绝后的约 9 秒内没有再次发送 lease-request，服务端仍只有一个已登记播放端，leaseHolderRendererId 和 leaseExpiresAt 均为 null。

实际采样如下。

```json
{
  "current": null,
  "playbackStatus": "idle",
  "rendererCount": 1,
  "leaseHolderRendererId": null,
  "leaseExpiresAt": null,
  "businessWebSocket": "OPEN",
  "leaseRequestCount": 1,
  "leaseResults": [{"ok": true}, {"ok": false, "code": "LEASE_EXPIRED"}]
}
```

### 原因与影响

本次差异删除了失败分支原有的延迟 lease-request。dropLeaseAndStopIfHeld 同时清空 leaseTimer 和 leaseDeadlineTimer，后续没有计时器负责重申请。首次申请收到 LEASE_HELD 也会进入这一分支，等待中的播放页同样停止申请。

当前 P0 的空租约动作可以结束，播放权却持续处于未恢复状态，初次等待和续租失败两条租约恢复路径均中断。此处属于原 WT-P0-007 的播放权恢复范围，继续沿用原编号。

### 修复与验收方向

保留按表演派发身份过滤停止与构造回执的修复，恢复 lease-result 失败后的受控重申请，并在断线或页面关闭时处理重试生命周期。

真实页面需覆盖续租被拒后重新取得租约，以及第二播放页首次被拒后在旧持有者退出时接管。验证应同时确认下一任务的成功终态和新租约的获取。

现有 [协议模拟脚本](D:/Project/dsh-workspace/WhaleTalk/scripts/lease-lost-e2e.mjs:132) 在拒绝分支自行执行 requestLeaseWithRetry，实际 main.ts 缺少此行为。该脚本通过无法证明页面实现具有相同恢复能力。

## WT-P0-011 · P2 · 连接超时与 close 重复排队，产生两个业务连接并破坏回执归属

主要位置在 [CONNECTING 守卫](D:/Project/dsh-workspace/WhaleTalk/src/web/shared/ws-client.ts:101)，相关位置为 [close 处理](D:/Project/dsh-workspace/WhaleTalk/src/web/shared/ws-client.ts:89)、[重连计时器](D:/Project/dsh-workspace/WhaleTalk/src/web/shared/ws-client.ts:44) 与 [消息处理](D:/Project/dsh-workspace/WhaleTalk/src/web/shared/ws-client.ts:81)。

### 复现与实际结果

1. 用隔离的本机 TCP 服务接收首个业务 WS 握手并保持不回应，令真实 Edge 的 WebSocket 保持 CONNECTING。后续连接使用正常 WhaleTalk 服务。
2. 等待新增的 10 秒守卫触发。
3. 守卫主动 close 并调用 scheduleReconnect。真实浏览器随后发送 close 事件，该回调再次调用 scheduleReconnect。
4. 约 0.8 秒及 1.6 秒后各建立一个正常业务连接，服务端认证并登记两次。单个页面出现两个 OPEN 的 /ws。
5. 在第一个连接仍持有租约时提交 dance。实际视频开始播放，但 ready 与 started 均被判为 stale-owner。此配置下旧租约到期后该任务以 LEASE_LOST 失败。

该连接超时场景独立运行两次，两次均出现两个业务连接。第二次继续提交实际动作，取得以下日志与快照。

```text
renderer-registered rnd-6ab4acb1 count=1
renderer-registered rnd-60a99729 count=2
dance dispatched rendererId=rnd-6ab4acb1
dance ready stale-owner
dance started stale-owner
dance session-settled failed LEASE_LOST
```

```json
{
  "openBusinessSocketsInOnePage": 2,
  "rendererCount": 2,
  "current": {"action": "dance", "stage": "waiting-playback"},
  "playbackStatus": "dispatching",
  "visibleVideo": "dance.webm"
}
```

### 原因与修复方向

connectSeq 只在新连接开始时递增，无法阻止同一次失败在两个回调中安排重连。第二个计时器在第一个新连接已成功后仍然执行，而且不会关闭该已建立连接。旧连接的 onmessage 缺少连接代数检查，仍更新同一页面的全局 rendererId 与表演状态，发送却走最新 ws，最终与服务端派发归属不一致。

让同一次连接失败只进入一次重连调度，管理唯一待执行重连计时器，并使已被替换连接的事件失效。用实际浏览器或忠实复现浏览器异步 close 的替身验证超时后仅一个连接、一个登记播放端，随后动作得到正常 ended。
