## WT-P1-009 · 同端口重复启动清除登记 / 不同端口共享日志

**修复一:重复启动守卫(`scripts/lib/test-server.mjs`)**

- `startTestServer` 前置校验:目标端口已有活跃登记(PID 文件存在,且该 PID 仍存活、命令行含本项目入口)时**抛错拒绝启动**,原登记原样保留;陈旧登记(进程已退出/PID 被复用)清理后放行。第二个进程不再有机会覆盖别人的 PID 后随 EADDRINUSE 退出并误删登记。
- `waitHealthy` 不再只看端口:联动子进程退出状态,子进程已退出(端口被占等)即判定失败——同端口旧实例的 200 不会被误判为新服务就绪。CLI 启动失败以非零退出码传递给调用方。

**修复二:日志按端口统一入口(`logFileFor(port)`)**

- `test-server.mjs` 导出 `logFileFor(port)` = `.tools/e2e-server-<port>.log`;`startTestServer` 的 `logFile` 参数改为可选,默认按端口生成。
- 启动 CLI、`e2e-reconnect-trace`、`e2e-selfheal-503`、`e2e-selfheal-verify` 全部走默认端口日志;`e2e-backup-takeover` 与 `e2e-dual-backup` 的日志读取改为同一入口 `logFileFor(port)`——两个端口并行时各自日志独立保留,候补类脚本的证据不再丢失或串端口。
- 顺带修复:`e2e-selfheal-verify` 原先直接 `spawn npm start`(退出只杀 npm 层,留下无主 tsx 服务,是多轮调试中孤儿服务的来源之一)——统一改经 `startTestServer` 启动登记、`stopTestServer(port)` 收尾。

**实测(复审验收口径)**:

- **场景 A(同端口重复启动后原实例仍可停止)**:首次启动 3210 → 200、PID 41196 登记 → 二次启动**退出码 1** 并报「端口 3210 已有活跃测试服务(PID 41196)」→ 原实例仍 200、登记文件仍为原 PID → `--stop --port 3210` 成功停止原实例(health 000)。
- **场景 B(不同端口并行各自日志保留)**:3210 与 3211 并行启动(各自 200、日志各 20 行)→ 停 3210 → 3211 仍 200 且其日志完好(含启动内容)→ 停 3211。
