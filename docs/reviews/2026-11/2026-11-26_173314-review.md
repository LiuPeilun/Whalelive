## WT-P3-002 · P2 · 前段失败时仍会在换声进程退出前释放配额

以 Windows 子进程替身运行真实唱歌模块。让搜歌进程等换声进程已启动后报错退出。任务记录 `fetch: fixture fetch failed` 并进入 `failed`，在途数回到 0。记录失败时以 PID 检查，换声进程仍活着，稍后才被结束。管线的 `finally` 只发起 `kill()`，随后上层立即结算与清理。收尾应覆盖换声工作进程尚在并行启动的场景，确保子进程退出后再交还配额。[管线收尾](../../../src/server/modules/singing/pipeline.ts#L486) · [任务结算](../../../src/server/modules/singing/index.ts#L203)

已复验上轮两个取消场景。两首歌等待工作进程就绪时急停，两个进程均退出，任务结算为 `failed(cancelled)`，在途数回到 0，没有触发回退。推理中急停也在进程退出后结算。上述 P1 场景已通过。[就绪等待中的取消](../../../src/server/modules/singing/pipeline.ts#L445) · [工作进程关闭](../../../src/server/modules/singing/pipeline.ts#L301)

## WT-P3-028 · P2 · 服务监听失败后仍留有启动预热进程

使用本机真实 RVC 启动隔离应用，正常调用 `app.close()` 前后，属于该 Node 实例的预热工作进程由 1 个变为 0 个。随后用本地监听器占住一处回环端口并启动另一隔离应用。启动以 `EADDRINUSE` 拒绝，进程列表仍显示一个由该 Node 实例启动的 `convert-worker.py`。预热在监听前启动，失败时应用未返回关闭句柄。可在应用完成初始化后启动预热，或在启动回滚时终止并等待子进程。[预热启动](../../../src/server/app.ts#L149) · [监听入口](../../../src/server/app.ts#L348) · [正常关闭](../../../src/server/app.ts#L366)
